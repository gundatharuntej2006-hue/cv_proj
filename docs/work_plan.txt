## 1. Project summary

1. **Input:** a frontal chest X-ray (DICOM or PNG), decoded, converted to grayscale and resized to 512×512.
2. **Gate:** an image-quality check plus a RAD-DINO kNN OOD score. Rejected images go to manual review.
3. **Analysis:** TorchXRayVision lung segmentation with a sanity check, then a lung crop with margin (full image if the check fails). A frozen RAD-DINO with a selected head gives the TB probability, and D-FINE detects single-class TB lesions.
4. **Decision:** temperature scaling (fitted on development), then a conformal lower threshold and a precision-constrained upper threshold (set on calibration) give **TB / REFER / NOT TB**. The detector link rule can move NOT TB to REFER.
5. **Output:** a worklist sorted by calibrated TB probability, with Grad-CAM, lesion boxes, a per-patient PDF and prediction logs. Every metric carries n and a 95% CI. Target: sensitivity ≥ 90% and specificity ≥ 70% (screen-positive = TB or REFER).

**"Prototype done" means all of the following are true:**
- `make demo` starts the Streamlit dashboard on the laptop. A mixed batch (DICOM, PNG, one corrupt file, one lateral view, one non-medical image) produces a worklist with every Section 11 field, a PDF per case and one log line per case.
- All 23 decision files (D01–D23) are locked, the no-test-tuning gate has passed, and the internal test has been run **once**. Tables 12.1–12.8 exist with n and CIs.
- One challenge submission has been made and logged, using the Section 4.6 category mapping fixed in D21. External validation (Section 13) and the comparative-experiments table (Section 14) are complete.
- Latency E6 has been measured and reported as pass or fail against < 2 s (GPU) and < 10 s (CPU).
- The report, slides and backup demo video are finished, and `main` is tagged `v-freeze`.

## 2. Precedence note

`docs/methodology.md` (Sections 1–21) is the **source of truth**. `docs/proposal.md` applies only where the methodology is silent. Where the two conflict, the methodology wins:

| Topic | Proposal (OUTDATED, do not implement) | Methodology (USE THIS) |
|---|---|---|
| Classifier | EfficientNet-B3 / ConvNeXt-Tiny primary | Frozen RAD-DINO primary, EfficientNet-B3 baseline |
| Detector | YOLO11, active/latent classes | D-FINE, single TB class; RT-DETRv2 is an extension |
| Lung segmentation | Train U-Net on Montgomery (Dice E1) | Pretrained TorchXRayVision + sanity check; report failure rate |
| Masking | Blank outside lungs | Crop to lung bounding box with margin |
| Imbalance | Focal loss | Weighted sampler / logit-adjusted loss |
| Splits | Dev cut from train; official val = internal test | Dev 10% of train; official val halved into calibration and internal test |
| Threshold | ROC-selected | Conformal lower + precision-constrained upper → TB / REFER / NOT TB |
| Temperature scaling | Fitted on validation | Fitted on development split only |
| Quality gate | Reject lateral / non-X-ray | Image-quality check + RAD-DINO kNN OOD gate; view head is an extension |
| CLAHE | Always on | Tested on/off once |
| Lung-crop ablation | E3 shortcut ablation | "Does lung cropping help?" (methodology Section 14) |

These proposal-only requirements are **retained** and each has an owner (see Section 9): DICOM anonymisation, corrupt-file robustness, threshold slider with the WHO default marked, prediction logging, per-patient PDF, latency E6, 1366×768 usability, scope-honesty text, Codabench log, Kaggle checkpoint-to-Drive, external-dataset fallback, and the Grad-CAM review with the guide.

## 4. Interface contracts, handshakes and governance

### 4.1 Contract rules

- People exchange data **only** through the versioned files (C01–C18) and frozen Python entry points (R1–R4) below.
- **Freeze:** all four sign off at the end of Week 1 (PR with 4 approvals, tag `contracts-v1`). After that, any change needs a CCR (`contracts/ccr/CCR-NNN.md`: what, why, affected consumers, migration). A CCR needs **2 approvals** (the producer and the affected consumer) and a notice to the P4 steward, bumps `schema_version`, and must update the producer's mock generator in the same PR. All four must approve only when the change touches `contracts/README.md`, the gate, or a contract that every stream consumes (C01, C14, C16, C18).
- Every contract has **exactly one producer**. `tbcore` validators run in CI against both mocks and real files.
- **Sealed data:** `tbcore.guard` refuses to load labels or images for `internal_test`, `challenge_test`, `external_test` and OOD role `ood_eval` unless the matching single-use unlock token from the gate (P4-09) exists. The one exception is `purpose="dedup"`, which reads images without labels (P2-04, H1).
- Filenames carry `_vN`. Mocks sit at the same relative path under `mock/` and are selected with `TB_MOCK=1` (`tbcore.paths`).

### 4.6 Challenge submission mapping (decided in W2, not in W9)

The TBX11K online challenge does **not** score the task exactly as this project defines it, so the mapping is
fixed in D21 before any model is trained and is reported as a known limitation.

| What the challenge scores | What this project produces | Mapping used | Consequence, stated in advance |
|---|---|---|---|
| Detection with categories: ActiveTuberculosis (1) and ObsoletePulmonaryTuberculosis / latent TB (2), plus category-agnostic handling of uncertain TB | One `tb_lesion` class (methodology §7, D16–D18) | Every predicted box is submitted as category 1, ActiveTuberculosis | Latent-TB average precision will be near zero **by construction**, not by failure. The category-agnostic figure is the only detection number we treat as comparable |
| Classification over healthy, active TB, latent TB and sick non-TB | Binary TB head, or three-class healthy / sick-non-TB / TB (D11) | `p(healthy)` and `p(sick_non_tb)` pass through; `p(active_tb) = p(tb)`, `p(latent_tb) = 0` | Any leaderboard metric that separates active from latent TB is not comparable with our internal numbers |

The single submission is therefore a **calibration point against the public leaderboard, not a headline result**.
Section 12.8 reports the returned metrics verbatim together with this mapping. If the challenge format has
changed by W9, P4 records the difference in the Codabench log and submits under the format then published.

## 5. Workload balance

Effort points: **1 point = 1 working day**, so a 4-point task is about one working week. Across 12 working weeks the 155 points come to **about three working days a week each**, every week, on top of a full 5th-semester course load. That is the deliberate choice recorded below: the full five-month scope delivered in three months. It leaves no slack, so the order in which work is dropped matters and is fixed in advance rather than argued about in W10. Phases: **A** W1–2 setup & data · **B** W3–5 components · **C** W6–8 locks & integration · **D** W9–10 sealed evaluation · **E** W11–12 product, report, freeze. **W13 is the only reserve week** and carries no planned work. Extensions are scheduled in W10–11 and start only after `core_complete` (H14).

| Person | A | B | C | D | E | **Core** | Ext | **Total** | Core vs mean (34.25) | Total vs mean (38.75) |
|---|---|---|---|---|---|---|---|---|---|---|
| P1 | 10 | 13 | 4 | 2 | 5 | **34** | 3 | **37** | −0.7% | −4.5% |
| P2 | 8 | 11 | 10 | 1 | 4 | **34** | 6 | **40** | −0.7% | +3.2% |
| P3 | 6 | 8 | 12 | 4 | 4 | **34** | 6 | **40** | −0.7% | +3.2% |
| P4 | 8 | 7 | 8 | 10 | 2 | **35** | 3 | **38** | +2.2% | −1.9% |
| Team | 32 | 39 | 34 | 17 | 15 | 137 | 18 | 155 | all within ±5% | all within ±5% |

**Cross-workstream exposure.** Every extension carries a named **reviewer from another workstream**, who reproduces the owner's result from the owner's script on their own machine before it enters C08 or C18, and who presents it at the teach-back. Half a day each, from the standing buffer. Swapping the extensions outright was considered and rejected: P2-18 writes C08 and P4-17 writes C18, so moving either task to the other person would put two producers on one contract and break rule 4.1. Reviewing gives the same exposure and keeps one producer per contract.

The loads are shaped differently on purpose: P1 is front-loaded (data), P3 peaks mid-project (detector), and P4 peaks in sealed evaluation. Everyone has work in every phase, at least one extension, and report writing. Half a day a week stays free as buffer (proposal A.1). If the schedule slips, the detector extensions are cut first; the core evaluation is never cut.

**Where the calendar is tight.** Two fortnights are effectively full-time for one person each. Phase A gives P1 10 points across W1–2, five days a week against the three-day average; three earlier changes keep it survivable (continuous integration moved to P3 as task P3-00, dataset checksums and the storage budget moved to W3 as P1-02b, and the CLAHE image store moved to W3 as P1-06b). The second is **P4's phase D**: 10 points of sealed evaluation across W9–10, also five days a week, and sequential because each step waits on a gate token. The fix is not more days, it is earlier days: tables 12.1–12.8 are written and tested against the P2 and P3 **mocks during phase C**, so phase D is only the run. If P1 slips anyway, P1-06a moves to W3 Day 1 and the split freeze moves from W2 Day 5 to W3 Day 2, which costs D03 two days and nothing downstream.

**Full scope in three months: what gives, and what does not.** This plan carries the five-month scope on a twelve-week calendar, at Atul's call. The arithmetic above is the cost: three working days a week each, with only the standing half-day a week and the single reserve week W13 as slack. Two consequences are worth fixing now rather than discovering in W9.

**The cut order, decided in advance.** When a week goes badly, drop in this order and tell the team in the weekly sync: (1) the extensions, all of them — P1-17, P2-17, P2-18, P3-16, P3-17, P4-17; (2) the second teach-back; (3) the comparative-experiment rows marked optional in Section 14. Never cut: the confidence intervals, the decision files, the single sealed run, or the external validation. A project with fewer experiments and honest numbers marks well. A project with many experiments and numbers nobody can defend does not.

**Time pressure must not buy extra looks at held-out data.** The no-test-tuning gate is unchanged: internal test once, challenge submission once, external once. A compressed schedule is exactly when a second look starts to feel reasonable — the result disappoints, there are two weeks left, and one more run seems harmless. It is not: at that moment the held-out set stops being held out and every number downstream of it becomes unreportable. If a sealed result disappoints, report it with its interval and write what you would do differently. That is worth more marks than a better number obtained by peeking, and it is the one thing in this project that cannot be repaired later.

**What the compression does to the risk profile.** On a three-month calendar the primary risk is simply running out of weeks, and the secondary one is that a slip in W2 is invisible until W9. The weekly 30-minute sync exists to make a slip visible the week it happens, not the month it happens: one written line per workstream saying what is done, what is blocked and whether the next milestone still holds. A milestone that will not hold is reported early and the cut order above is applied; it is never recovered by quietly skipping a confidence interval or a decision file.

## 8. Risks and mitigations

| Risk | Mitigation | Owner |
|---|---|---|
| Compressed calendar: three days a week each with no buffer, so one bad week cascades, and decisions made in W2 are half-remembered by W9 | Weekly 30-minute sync with a written one-line status per workstream; every decision is a committed JSON file with its criterion pre-registered, never a conversation; teach-backs in W8 and W11 force each person to re-read someone else's decisions; W13 held in reserve for assessment weeks | All, P4 stewards |
| Class imbalance and the tiny latent class (1,200 TB vs 10,000 non-TB; 212 latent, 54 combined) | Weighted sampler or logit-adjusted loss chosen on development (D10); single-class detector; subtype-stratified results reported with an explicit "not reliable" caveat for latent TB; balanced metrics only | P2, P3 |
| Challenge labels withheld → accidental tuning on reported data | Committed split file, sealed-split guard, decisions registry, single-use gate tokens, exactly one challenge submission recorded in the Codabench log | P4 |
| Model and data licences | D-FINE (Apache-2.0) replaces the proposal's copyleft detector risk; RAD-DINO is MIT (verified 29-09-2026), so the backbone carries no academic-use restriction; CheXpert and other OOD sources remain under their own research terms; all recorded in D05/D15/D20 and stated in the report | P1, P2, P3 |
| Shortcut learning / cross-dataset collapse | Lung crop with margin (no black border); "Does lung cropping help?" comparison (AUC drop internal → external, pointing accuracy); Grad-CAM review with the guide; external results reported as they are | P2, P3, P4 |
| 6 GB VRAM and Kaggle limits | Frozen RAD-DINO with offline embeddings verified in W1 (P2-01); detector trained on T4 with AMP and small batches; checkpoint to Drive every epoch (P3-02); EfficientNet-B3 and D-FINE runs on separate Kaggle accounts; Colab as backup | P2, P3 |
| A third external site does not arrive (Shenzhen and Montgomery no longer carry this risk: downloaded directly, no application) | TB Portals application sent in W1; fallback decided by W6 (D04), e.g. a public TB CXR set checked for overlap with TBX11K; the report names the external set actually used | P1 |
| Over-reading explanations | Heatmaps captioned "attention evidence, not a finding"; localisation agreement reported as overlap with incomplete boxes, not proof of clinical correctness; same caveat in the PDF | P3 |
| Over-claiming clinical readiness | Single-source disclaimer + scope-honesty text on every screen and PDF; report states there has been no prospective clinical validation | P4 (text), P1 (screens), P3 (PDF) |
| Conformal guarantee does not transfer (exchangeability broken externally) | Measured on external data (P4-14); recalibration extension shows local-data needs (P4-17); stated as finite-sample control under assumptions only | P4 |
| Precision target unreachable on calibration | By design the TB category is left empty and all screen-positive cases go to REFER; reported, not tuned | P4 |
| Small calibration split (~100 TB) → coarse thresholds, wide CIs | Every result reports n and a CI; no post-hoc threshold change | P4 |
| Segmentation fails on external images | Full-image fallback, logged; failure rate reported per dataset (12.7) | P1 |
| OOD gate rejects valid external X-rays | External pass rate reported (12.6, §13); threshold not retuned on external data | P2, P4 |
| Contract drift / integration slip | Frozen contracts, validators in CI, mocks from Day 3, CCR with 4 approvals, weekly integration check against mocks | P4 |
| Detector AP too low to be useful: only about 540 training images carry boxes | Trigger in P3-06 (development AP50 < 0.05 at the better input size). **Contingency, pre-registered in D21:** the detector is reported as an honest negative result with its CI; the link rule is disabled and its Section 14 row records "not evaluable, detector below threshold"; the worklist and PDF drop the lesion panel and keep the Grad-CAM evidence; the classifier path remains the deliverable. Never fixed by re-tuning on sealed data | P3, P4 |
| Challenge scoring does not match the project's task definition | Mapping fixed in D21 and Section 4.6 in W2, long before the single submission; latent-TB AP expected near zero by construction and reported as such; the submission is treated as a leaderboard calibration point, not a headline result | P4 |
| P1 front-loaded: W1–2 is exactly 10 points with no buffer | CI moved to P3-00; P1-02b and P1-06b moved to W3. If P1 still slips, P1-06a moves to W3 Day 1 and the split freeze to W3 Day 2 | P1, P3 |
| Process overhead crowds out the science | Formal JSON Schema kept only for C01, C14, C16 and C18; the rest are short specs with dtype checks; a CCR needs 2 approvals, not 4. The split file, decisions registry, sealed-split guard and gate are **not** negotiable | P4 |
| Team member unavailable | Consumer-reviewer knows each interface; every task has written acceptance tests; weekly half-day buffer | All |
